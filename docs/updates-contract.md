# Обновление моделей и независимый контроль

## Операции

- retrain: обучение новой версии с нуля. Для совместимой схемы сохраняется parent_id. Нормировка/предобработчик обучаются заново только на train новых данных.
- fine-tune: только MLP, инициализация сохранёнными весами. Предобработчик, mean/std, порядок признаков, скрытые слои и dropout фиксированы. Adam создаётся заново: старое состояние оптимизатора в прежнем формате не сохранялось. Это продолжение обучения весов, не побитовое возобновление прежней сессии.

Обе операции записывают отдельный запуск и неизменяемую версию в тот же Store. Родительский комплект не меняется. В manifest/update.json указаны операция, parent/origin version, настройки, метрики, состав данных и политика оптимизатора. Контрольная выборка не передаётся в обучение.

Для таблиц схема по умолчанию берётся у родителя. retrain --config допускает новую конфигурацию. Если изменились цель, набор/порядок/типы признаков либо временная конфигурация, создаётся новая модель без parent_id; origin_version остаётся для аудита. fine-tune не принимает конфигурацию другой схемы и отклоняет изменение hidden-sizes. Входные столбцы могут переставляться: именованная схема сохраняется.

Для спроса поддерживается demand-v2 с тем же набором услуг; вход — подготовленный каталог monthly_demand.csv/preparation.json. Лаги, рекурсия validation/test и границы сохраняют правила итерации 3. При дообучении статистики родителя не переоцениваются. Для цены — каталог price_analysis.csv, та же формульная цель; validation/test считаются в денежных единицах с ограничением 85–115%. Legacy-спрос нужно обучить как новую demand-v2 модель через обычный конвейер.

MLP использует новые train/validation/test и early stopping; лучшая версия за текущие эпохи не обязана быть лучше родителя. Исходная модель остаётся доступной. Обучение на дополнительных данных может использовать только новый набор или набор с историей — состав фиксируется явно; предобработчик при fine-tune одинаков в обоих случаях.

## Учёт данных

Новые высокоуровневые обучения сохраняют provenance в manifest:

- таблицы: SHA-256 нормализованных значений выбранных признаков (и даты origin во временном режиме), без целевого значения;
- спрос/цена: SHA-256 ключа service_id/year/month, без цели;
- количество предоставленных строк, политику идентификации и временные границы, где применимо.

Для консервативной проверки учитываются все предоставленные размеченные строки, включая validation/test, а у предметных сценариев — весь предоставленный календарь. Fine-tune наследует объединение отпечатков всех данных, повлиявших через прежние веса. Scratch-retrain имеет собственный состав данных. При неизвестном происхождении унаследованных весов provenance помечается неполным.

Это проверка по зарегистрированным наблюдениям, не доказательство происхождения реальных данных. Для обычных таблиц одинаковые профили признаков считаются потенциальным пересечением даже у разных объектов: возможен консервативный отказ. Изменение только цели не скрывает повторное использование строки. Временной контроль должен идти позже всех ранее предоставленных целей/месяцев.

Комплекты, созданные до введения provenance, остаются пригодными для прогноза и обновления. Однако подтвердить независимость сравнения с такой версией нельзя: compare-versions отказывает с объяснением. Для проверяемого эксперимента создайте новую корневую модель на заранее отделённых данных и сохраняйте контроль отдельно.

## Общая контрольная выборка

compare-versions принимает два или более ID одной задачи и совместимой исходной схемы. Он не обучает, не выбирает настройки и не меняет версии. Если контроль пересекается с зарегистрированными данными любой версии или происхождение не подтверждено, независимый отчёт не публикуется; неуспешный запуск остаётся в истории.

Для таблицы нужен CSV/XLSX с теми же признаками и известной числовой целью во всех контрольных строках. Каждая версия применяет свой сохранённый предобработчик. Известные категории и статистики не дообучаются. Для временной таблицы дата начала контроля должна быть позже границы ранее предоставленных целей.

Для цены контроль — CSV/XLSX формата price_analysis с новыми месяцами, без дубликатов service/month. Это сравнение воспроизведения рекомендации на месячных строках в денежных единицах, не будущей рыночной цены и не прибыли.

Для спроса контроль — отдельная таблица service_id/year/month/total_bookings на 1–3 последовательных месяца для всех услуг. Прогноз от одной общей точки рекурсивен: факты контроля используются только при подсчёте метрик. По умолчанию общая доступная история берётся из наиболее позднего context сравниваемых версий. При необходимости --history задаёт полную общую месячную историю отдельно. Она обязана заканчиваться непосредственно перед контролем. Все модели получают одинаковую историю, но используют свои фиксированные статистики. Снимок истории и её отпечаток входят в отчёт.

Отчёт: control_comparison.json, comparison.csv, comparison_predictions.csv, comparison.html, results.xlsx, control.csv и, для спроса, history.csv. Указаны версии/родители/алгоритмы/настройки, состав и отпечаток контроля, условия, факты/прогнозы и MAE/MSE/RMSE/wMAPE/R². Неопределённые метрики остаются null. Автоматического повышения модели по контрольному результату нет; не используйте его для повторного подбора параметров.

Результаты лежат в store/runs/<run-id>. Операция сравнения не создаёт новую модель. Повторные сравнения на одном контроле сами по себе не делают его независимым от ручного подбора — это ответственность постановки эксперимента.
