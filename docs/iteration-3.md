# Итерация 3: исправленный месячный спрос

Статус: реализована. Новый режим demand-v2 используется по умолчанию. Старый legacy-parity доступен явно для проверки переноса; методики и checkpoint не смешиваются автоматически.

## Исправления относительно ServiceFlow

1. Цель — непосредственно total_bookings (количество завершённых записей), без деления на среднее по всей истории. Статистики масштабирования признаков вычисляются только на train. Цель не масштабируется.
2. as-of — граница доступности данных: его календарный месяц всегда исключён. Например, 2026-11-14 оставляет данные по октябрь включительно; 2027-01-01 включает весь декабрь 2026. Даже последний день месяца исключает этот месяц — для включения нужно указать начало следующего. Применяется календарь выгрузки, не неявное преобразование часового пояса.
3. monthly_demand.csv хранит полную месячную сетку по всем услугам, включая нулевой спрос. Нулевые месяцы сырого экспорта формируются явно. Для готовой таблицы пропуск месяца — ошибка, не автоматическая подстановка. Дата начала общая: первый завершённый визит; история появления услуг отдельно не моделируется.
4. Одна функция feature_vector строит три лага, среднее последних трёх, отношение среднего последних трёх к среднему доступных предыдущих (до трёх) и календарные sin/cos. Нужны три предыдущих месяца; если предыдущего окна нет или его среднее равно нулю, тренд равен 1. Текущая цель никогда не входит в её признаки.
5. Каждый ряд имеет собственную историю. Следующие 1–3 месяца строятся рекурсивно только из предсказаний. Нет ограничений 0.3–2.0 и нижней границы спроса выше нуля: отрицательный выход модели обрезается до нуля. Прогноз — ожидаемое количество записей, может быть дробным; до целого он не округляется.

## Разбиение и оценка

Первым трём месяцам не хватает лагов, они остаются контекстом. Из оставшихся месяцев последние три — test, предыдущие три — validation, остальные — train. Для обучения нужно минимум десять полных календарных месяцев (три контекста, один train, три validation, три test). Точные даты и число строк каждого раздела сохраняются.

Веса обучаются на train. Каждые validation_interval эпох качество проверяется рекурсивным прогнозом трёх validation-месяцев от одной точки непосредственно перед validation. Лучшие веса выбираются по MSE этого прогноза. Факты validation не подставляются в следующие шаги и не используются для обновления весов.

Финальный test имеет два отдельных отчёта в исходных единицах:

- one_step: последовательный прогноз на один месяц с фактической историей, доступной перед каждым месяцем; явно обозначен rolling-one-step-observed-history;
- recursive_test: трёхмесячный прогноз от точки перед test, без обновления по фактам test; показатели для каждого lead=1/2/3 и объединённые по трём месяцам.

На одном и том же origin сравниваются MLP, последнее значение и среднее трёх. Рекурсивные baseline также пополняют историю своими предсказаниями. Для нового режима рассчитываются MAE/MSE/RMSE/wMAPE/R²; wMAPE при нулевой сумме фактов и неприменимый R² возвращают null с соответствующим определением в контракте. Итерация 5 ещё должна добавить линейную модель и унифицировать отчёты всех сценариев.

Это один фиксированный контрольный origin, а не множество независимых временных окон: особенно при малом числе услуг оценка имеет ограниченную представительность. Число эпох пока исходное, early stopping и публичная настройка seed относятся к следующим этапам. Менять настройки по результатам test нельзя.

## Модель и история

Checkpoint сохраняет demand_context: версию 2, частоту MS, цель, правило признаков, as_of, границы разделов и полную агрегированную историю по услугам. Веса остаются выбранными на validation; на всю историю после оценки модель автоматически не переобучается. При прогнозе после последнего известного месяца его факты доступны и законно используются как лаги, включая ранее отложенные месяцы; это не влияет на сохранённую оценку.

Для predict достаточно checkpoint и текущих materials.json/service_materials.json. Если подан monthly_demand.csv, требуется также preparation.json: можно только дописать полные месяцы, сохранив набор услуг и всю предыдущую историю неизменными. Исправление прошлого или смена услуг требует новой модели. Предобработчик при прогнозе не переобучается.

Старый ratio-checkpoint в demand-v2 отклоняется. Для его применения используются `--mode legacy-parity` и старые prepared-файлы; legacy-режим сохраняет ограничения исходной методики. В обоих режимах по-прежнему нужно доверять источнику pickle-checkpoint.

## Закупки

Расчёты разделены: forecast → consumption → purchase. Норма задаётся в unit материала на одну запись; остаток и минимальный запас — в той же unit, price — за одну unit. Обязателен purchase_step >0. Дробные нормы, остатки и шаги допустимы в demand-v2.

Потребность суммируется по всем услугам и месяцам. Недостача = max(0, потребность + минимальный запас − остаток); закупка округляется вверх до кратного purchase_step. Стоимость считается по округлённой закупке, округляется до двух знаков HALF_UP. Вычисления закупки используют Decimal. Это одна закупка на весь горизонт, без повторного вычитания остатка и без планирования поставок.

## Проверки и ограничения

Проверены исключение неполных/будущих месяцев, причинность признаков, изоляция рядов, совпадение статистик/весов при изменении test, рекурсия и переход года, нулевой спрос, неопределённые метрики, дробные нормы/шаги/денежное округление, восстановление в новом процессе и добавление новой истории без изменения прошлой.

Пример известной закупки: две услуги, по одной ожидаемой записи за месяц; нормы 0.1 и 0.2 ml. За три месяца нужно 0.9 ml; остаток 0.2, минимум 0.1, шаг 0.25 → закупка 1 ml. При цене 2.675 за ml стоимость 2.68. При достаточном остатке закупка нулевая.

Цена остаётся рекомендацией по формуле. Подготовка в demand-v2 ограничивает и её таблицу полными месяцами, но формула, признаки и модель цены не переработаны. Исторические цены справочников по-прежнему не восстанавливаются из текущих цен.

Новые файлы: demand.py (признаки, рекурсия, оценка), demand_pipeline.py (IO и запуск), purchasing.py (нормы и закупка). Старый сценарий в scenarios/materials.py используется только при явном legacy-parity. Реальные данные не публиковались; ServiceFlow_back не изменялся.

Итог проверки: `python -m pytest -q` — 23 passed (pytest из /tmp/predictml-test-deps, текущий Linux/CPU). Дополнительно CLI прошёл prepare → train-predict materials (50 эпох, 3 месяца), train-predict price (50 эпох), а отдельный процесс predict проверяется сквозным тестом. Это проверки работоспособности, не обещание заданного качества модели. `git diff --check` ошибок не обнаружил. Итерация 3 завершена; следующая — 4 (универсальные CSV/XLSX и сохраняемая предобработка).
