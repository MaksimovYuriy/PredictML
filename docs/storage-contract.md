# Комплекты моделей и история, формат 1

Высокоуровневые train-table, compare и train-predict автоматически используют Store в --output. Повторное обучение в том же каталоге создаёт новые UUID и не перезаписывает сохранённые версии. Чистые функции ядра train_table/fit не обращаются к SQLite; их старые save/joblib/pth интерфейсы остаются низкоуровневыми способами сохранения без регистрации.

## Структура

```text
store/
  history.sqlite3
  runs/
    <run-id>/
      ... результаты, отчёты и экспорт конкретного запуска ...
      versions.json
      versions/
        <version-id>/
          manifest.json
          model.joblib либо model.pth
  ... совместимые копии файлов последнего запуска ...
```

SQLite хранит запуски (операция, статус running/completed/failed, параметры, UTC-время начала/окончания, ошибка, каталог результатов, входной version ID) и версии (ID, run ID, задача, алгоритм, цель, схема, относительный путь комплекта и SHA-256 manifest). С итерации 7 команды обновления назначают parent_id для совместимой схемы; смена цели/признаков создаёт новую модель с origin_version без parent_id.

Один --output можно использовать как хранилище нескольких задач. Если указаны разные каталоги, у каждого своя SQLite-история. При одновременных запусках авторитетны каталоги по run ID; плоские копии последнего результата не являются согласованным снимком нескольких параллельных задач.

## Manifest

Каждый комплект содержит:

- bundle_format=1, version_id, run_id, created_at, task (tabular/materials/price), model_kind;
- схему исходных признаков, их порядок/типы и цель; у demand-v2 отдельно указаны исходные поля истории и производные признаки;
- архитектуру и настройки обучения, seed, метрики;
- обученный предобработчик внутри tabular payload либо фиксированные mean/std checkpoint; порядок преобразованных признаков;
- временную конфигурацию и сохранённую историю спроса;
- версии Python/PredictML и библиотек;
- точный список payload-файлов с размером и SHA-256.

seed=null означает, что исходный путь обучения не задавал seed; значение не выдумывается задним числом. Современные compare и train-table фиксируют выбранные настройки/seed. Состояние модели и предобработчика сохраняется независимо от исходных CSV/Rails/БД.

## Запись и сбои

До работы создаётся SQLite-запуск running. Файлы и комплекты пишутся в уникальный .pending-каталог. Готовый каталог переименовывается в runs/<id>, затем одной SQLite-транзакцией регистрируются все его версии и completed. При обычной ошибке каталог убирается и запуск становится failed; частичная регистрация нескольких версий откатывается целиком. Существующие версии не изменяются.

Файловая система и SQLite не образуют общей распределённой транзакции. При жёстком завершении процесса между переименованием и commit могут остаться незарегистрированные файлы и running-запуск. Они не выдаются как готовые версии. После проверки, что процесс действительно остановлен, recover-run помечает конкретный запуск failed, сохраняя файлы для разбора. Автоматически объявлять все running-запуски прерванными нельзя: они могут выполняться в другом процессе. Гарантии физической сохранности при отказе носителя не заявляются.

После commit плоские пути вроде model.joblib/material_model.pth обновляются как совместимые копии последнего запуска. Только эти копии могут перезаписываться. Если их обновление не удалось, программа сообщает предупреждение с авторитетным каталогом завершённого запуска; версия в SQLite остаётся доступной. Не используйте эти копии как архив.

## Загрузка и совместимость

Store.load(version_id) проверяет запись SQLite, расположение, хеш manifest, обязательные поля, формат, хеш/размер payload и зависимости до десериализации. После чтения проверяются схема, архитектура, нормировка и предобработчик относительно manifest. Не поддерживаемые или повреждённые комплекты отклоняются с ValueError.

Консервативная политика: одинаковые major/minor Python и точные версии numpy/pandas/torch/scikit-learn/scipy/joblib. openpyxl и версия приложения записываются информационно; поддержка формата определяется bundle_format и внутренним форматом payload. Автоматической миграции на другие версии библиотек нет.

Самодостаточный каталог версии можно скопировать и загрузить без SQLite через TabularModel.load(bundle_directory) или Predictor.load(bundle_directory). При такой загрузке нет внешнего SQLite-хеша manifest, но структура, payload-хеши и совместимость всё равно проверяются. SHA-256 проверяет целостность, а не авторство: pickle/joblib нужно получать из доверенного источника.

Старые отдельные .pth/.joblib поддерживаются для совместимости и не имеют гарантии целостности manifest. Ранее созданные файлы сами в SQLite не импортируются; новые высокоуровневые обучения регистрируются автоматически.

## Прогноз по ID и экспорт

predict-version использует только выбранный version ID. Табличная модель принимает новый CSV/XLSX по сохранённой схеме. Спрос использует сохранённую историю или её допустимое дополнение и актуальные JSON-справочники материалов. Цена использует свой прежний контракт подготовленного CSV. Обучение не запускается.

Прогноз записывает новый запуск со ссылкой input_version и файл prediction.json с provenance. Экспорт csv/xlsx/both; XLSX имеет отдельные листы predictions либо demand/materials/material_months либо prices, а также metrics. Разделение materials/material_months предотвращает дублирование закупки при помесячном просмотре. Метрики — характеристики сохранённой версии, они не пересчитываются на новых строках без известных целей.

export-metrics выгружает метрики выбранной версии в CSV/XLSX. Вложенные числовые/скалярные поля представлены путями field/value; списки исходных наблюдений и кривые не дублируются в таблице, полный JSON остаётся в manifest. Неопределённые метрики — пустые ячейки, исходное null сохраняется в manifest.

Авторитетный результат всегда в store/runs/<prediction-or-export-run-id>. --output создаёт удобную копию; при ошибке копирования рассчитанный результат остаётся в истории. Восстановление копии не требует нового обучения. Нельзя направлять обучение или экспорт внутрь архивного каталога этой истории.

Обновление и независимое сравнение версий реализованы в итерации 7; см. updates-contract.md. Проверка контроля использует provenance в новых manifest; старые комплекты без него по-прежнему загружаются для прогноза.
