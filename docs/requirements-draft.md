Программа будет использоваться в учебном курсе по прогнозированию. Она должна демонстрировать полный цикл: загрузка данных → подготовка признаков → обучение → оценка → сохранение → прогноз → повторное обучение и дообучение.

### 2. Цель программы

Пользователь должен иметь возможность загрузить собственную таблицу CSV/XLSX, выбрать целевую переменную и признаки, обучить модель, оценить качество и получить прогноз на новых данных.

Универсальность относится к созданию модели под выбранную схему таблицы. Уже обученная модель принимает данные, совместимые с сохранённой схемой.

При изменении целевой переменной или набора признаков создаётся новая модель.

Первая версия поддерживает числовую регрессию на табличных данных, включая временное прогнозирование через подготовленные признаки.

### 6. Предобработка

Реализуй единый сохраняемый конвейер:
- заполнение пропусков признаков;
- масштабирование числовых признаков;
- кодирование категорий;
- преобразование дат;
- при необходимости лаги, скользящие статистики, тренд и сезонные признаки.

Параметры заполнения, масштабирования и кодирования обучаются только на обучающей части.

Для временных данных:
- соблюдай хронологию;
- лаги и скользящие признаки не должны использовать будущее;
- учитывай отдельные ряды, если таблица содержит несколько услуг или объектов;
- явно задавай частоту, горизонт и способ построения целевой переменной;
- используй только признаки, доступные на момент прогноза.

Не считай выбор столбца даты достаточным для автоматического определения задачи прогнозирования.

### 7. Модели и обучение

Реализуй:
1. Простой baseline, соответствующий задаче.
2. Линейную модель.
3. MLP на PyTorch с использованием решений исходного проекта.

MLP должна определять размер входного слоя после предобработки. Архитектура не должна зависеть от фиксированного списка признаков ServiceFlow.

Предусмотри настройку:
- скрытых слоёв;
- learning rate;
- числа эпох;
- batch size;
- seed;
- early stopping.

Разделяй данные на train, validation и test. Для временного режима используй хронологическое разделение.

Валидационная часть используется для выбора настроек и лучших весов. Тестовая часть — для итоговой независимой оценки.

Не требуется, чтобы MLP обязательно превосходила линейную модель. Требуется корректное сравнение.

### 11. Основной сценарий: спрос и закупки

Сохрани и адаптируй логику исходного модуля материалов.

Раздели:
1. Прогноз спроса — количества заказов или записей.
2. Расчёт потребности в материалах.
3. Расчёт закупки и её стоимости.

Базовая логика:
- расход = прогноз спроса × норматив расхода;
- потребность суммируется по услугам или продуктам;
- закупка = max(0, потребность + минимальный запас − текущий остаток);
- стоимость = закупка × цена единицы.

Правила округления и единицы измерения должны быть явными.

Проверь поддержку горизонтов один, два и три месяца в исходной реализации. Опиши и реализуй согласованный способ многопериодного прогноза без использования фактических будущих значений.

### 12. Дополнительный сценарий: рекомендация цены

Не называй такой результат прогнозом наблюдаемой будущей цены.

Сценарии цены и спроса должны использовать общее ядро, различаясь конфигурацией и предметной обработкой данных.

## Согласованные уточнения

Статус: требования и уточнения ниже согласованы пользователем 14 ноября 2026 года. Исходные требования применяются с учётом этих границ первой версии.

1. Первая версия включает универсальную табличную регрессию и временные признаки с явной конфигурацией. Автоматическое рекурсивное прогнозирование нескольких периодов реализуется для сценария месячного спроса ServiceFlow с выбором горизонта 1, 2 или 3 месяца. Универсальное автоматическое прогнозирование произвольных рядов на любых частотах не входит в обязательный объём v1.
2. В сценарии ServiceFlow спрос — количество завершённых записей по каждой услуге за календарный месяц. Для обучения используются только полные месяцы; дата отсечения фиксируется. Общий табличный режим сохраняет выбор целевой переменной пользователем.
3. Закупка рассчитывается однократно на весь выбранный горизонт. Текущий остаток и минимальный запас учитываются один раз. Единица измерения и положительный шаг округления задаются явно для каждого материала; закупаемое количество округляется вверх до кратного шагу. Стоимость рассчитывается по округлённому количеству и округляется до двух десятичных знаков. Регулярные поставки и помесячное управление остатками не входят в обязательный объём v1.
4. Демонстрационные данные по умолчанию синтетические и явно обозначаются. Выбор между синтетикой и обезличенным экспортом не был отдельно определён ответом пользователя; использование и публикация реального экспорта требуют отдельного согласования. Это не препятствует реализации и проверке на синтетических данных.
5. Рекомендация цены остаётся дополнительным сценарием v1 на общем ядре. Формульное происхождение цели явно объясняется пользователю.
