# Итерация 1: контракты и контрольные примеры

Реализовано: контракты docs/contracts.md; валидация сырого экспорта перед подготовкой и подготовленных файлов перед обучением/прогнозом. Ошибки числовых значений указывают таблицу, столбец и первые номера строк CSV. Проверяются идентификаторы, связи, статусы, даты, числа, дубликаты ключей и минимальная история.

Сохранены неизменённые исходные Ruby-сервисы в tests/reference. run.rb заменяет только границы получения данных, календаря и записи файлов, вызывая фактические методы исходных классов. Сравнение запускается локальным Ruby без Rails и PostgreSQL на синтетической восьмимесячной истории с нулевыми месяцами и одной услугой без визитов. Обе подготовленные таблицы сравниваются целиком. Это проверяет вычисления, но не исполнение исходного SQL и не экспорт из настоящей БД.

Выявленные изменения переноса:

- Изначальный Python использовал round (banker's rounding), Ruby — округление половины от нуля. В подготовке введено decimal half-up на границе экспорта; случай ±2.675 закреплён. Внутренние вычисления по-прежнему float: абсолютное совпадение для всех возможных двоичных пограничных значений не заявляется. Исходный Python-прогноз и его round не изменены.
- В начальном синтетическом примере client_id начинались с 0. Они сдвинуты на 1 для соответствия положительным ключам; группировки и результаты не изменились.
- Неизвестные статусы, связи и пустые остатки отклоняются явно. Это намеренное ужесточение входной границы, а не изменение методики обучения.

Проверки закупки используют исходный predictor с постоянным выходом модели: на двух услугах по 10 записей и нормах 2/3 месячный расход равен 50. При остатке 10, минимуме 5 и цене 20 закупки на 1/2/3 месяца равны 45/95/145, стоимости — 900/1900/2900. Отдельно проверены переход декабря в январь и достаточный остаток с нулевой закупкой. В этих проверках модель заменена заглушкой: они не оценивают качество обучения.

Известные методические проблемы из аудита остаются без изменений до итерации 3. Глобальные параметры адаптера и дублирование скриптов устраняются в итерации 2. Полная совместимость схемы с checkpoint — дальнейшие этапы.

Итог проверки: `python -m pytest -q` — 10 passed (в текущем окружении pytest установлен отдельно в /tmp/predictml-test-deps и запускался с соответствующим PYTHONPATH). Исходная попытка установки без доступа к сети не прошла; последующая установка с сетевым доступом успешна. Тесты совместимы с unittest, Ruby-сравнение пропускается при отсутствии Ruby с явной отметкой skip. Для обычной установки инструментов проверок: `python -m pip install -e '.[test]'`.

Статус: итерация 1 завершена в описанной области; проверка настоящего SQL/БД не выполнена. Следующая — итерация 2, выделение общего ядра из legacy.
