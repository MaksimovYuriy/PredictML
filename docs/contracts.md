# Контракты ServiceFlow → PredictML, версия 1

Область: существующий сценарий ServiceFlow, не будущая универсальная схема таблицы. Подготовка и прогноз не обращаются к БД. Дополнительные столбцы CSV допускаются и не используются. Все CSV — UTF-8 (допустим BOM), запятая, одна строка заголовков без дубликатов. Пустая таблица может иметь только заголовок, но services и завершённые notes не могут быть пустыми.

## Сырой экспорт

| Файл | Поля и условия |
|---|---|
| notes.csv | service_id — положительный целый FK services.id; client_id — положительный целый ключ для группировки; status — 0/1/2 либо pending/canceled/completed; start_at — ISO-дата/время без часового пояса; total_price — конечное число ≥0 |
| services.csv | id — уникальный положительный целый; price — конечное число >0; active — true/false или 1/0 |
| materials.csv | id — уникальный положительный целый; title — непустая строка; quantity/minimal_quantity — целые ≥0; price — конечное число ≥0, пропуск означает 0 |
| service_materials.csv | service_id/material_id — положительные целые FK соответствующих справочников; required_quantity — целое ≥0 |

Все поля обязательны, кроме значения materials.price. В остальных числовых полях запрещены пропуски, NaN и бесконечности. Для количества и норм сохраняется целочисленная схема исходной БД. Строки service_materials не обязаны иметь уникальную пару: исходная схема этого не требует, поэтому повторные нормы суммируются. Идентификатор записи notes.id не входит в контракт: одинаковые строки могут представлять разные визиты и не удаляются автоматически.

Выгрузка не требует персональных полей клиента, телефона или имени. client_id используется только как ключ. У всех дат должен быть один заранее выбранный календарь экспорта; не выполняется неявное преобразование часового пояса. Временные зоны/смешанные форматы нужно нормализовать до загрузки.

as-of — явная дата без часового пояса. Режим совместимости включает её календарный месяц целиком; не обрезает визиты по дню. Календарная сетка начинается с первого завершённого визита, пропущенные месяцы считаются нулевыми для всех услуг. Нужны минимум четыре календарных месяца. Все статусы валидируются, затем для расчёта остаются только completed/2. Первые посещения — все завершённые визиты клиента в месяце его первого завершённого визита, как в исходном SQL.

Контракт строже Rails в отношении nullable quantity/minimal_quantity: такие остатки отклоняются, поскольку исходный Python не умеет считать закупку с null. Неизвестные статусы также отклоняются вместо молчаливого игнорирования. Прямой экспорт уже агрегированных файлов не восстанавливает исходные визиты.

## Подготовленный экспорт

### material_forecast.csv

Поля в исходном порядке:

`service_id, total_bookings, avg_bookings, booking_ratio, bookings_lag_1, bookings_lag_2, bookings_lag_3, avg_bookings_last_3m, usage_trend, month_sin, month_cos, year, month`.

Одна строка на услугу и месяц; ключ (service_id, year, month) уникален. Первые три месяца сетки исключаются. Услуги с нулевым средним по всей сетке исключаются. total_bookings — целое ≥0; avg_bookings >0 и одинаково внутри услуги. Отношение, лаги, среднее и тренд — конечные числа ≥0. Сезонные признаки в [-1,1]. month — 1–12, year — 1–9999.

Для обучения проверяется непустота train/validation/test в календарных окнах исходного тренера (последние три месяца — test, предыдущие три — validation). Это минимальное условие запуска, не гарантия достаточного объёма для качественной модели. Непрерывность истории и отсутствие утечки этот валидатор не доказывает: исправление временного конвейера — итерация 3.

### price_analysis.csv

`service_id, base_price, is_active, total_bookings, revenue, avg_price_fact, first_visit_share, year, month, avg_material_cost_per_service, material_cost_share, target_price`.

Ключ и календарь аналогичны. base_price >0; is_active — 0/1; first_visit_share в [0,1]; остальные измерения конечные ≥0, total_bookings целое. Для обучения нужно минимум семь различных месяцев до последнего календарного года; последний год исходный сценарий резервирует для рекомендаций.

target_price задаётся правилом: base_price × (1 + 0.05 × total_bookings / max_bookings_среди_услуг_за_месяц − 0.03 × first_visit_share), с ограничением 85–115%. Нулевой максимум заменяется единицей. Это рекомендация, не наблюдаемая будущая цена.

### JSON-справочники

Оба файла содержат массив объектов, числовые поля — JSON numbers, не строки. Дополнительные поля игнорируются.

- materials.json: id (уникальный положительный целый), title (непустой), current_quantity/minimal_quantity (целые ≥0), price (конечное число ≥0).
- service_materials.json: service_id/material_id (положительные целые), required_quantity (целое ≥0). material_id обязан присутствовать в materials.json. service_id может отсутствовать в material_forecast.csv: исходный экспорт исключает услуги без спроса, но сохраняет их нормы; такие нормы не дают расхода.

Единицы в исходном контракте не представлены отдельным полем: остаток и норматив должны быть в одной единице материала, цена — за эту единицу. Явные единицы и шаг округления будут добавлены в итерации 3 с изменением версии контракта.

## Выходные контракты

Материалы: массив объектов material_id, title, current_quantity, minimal_quantity, unit_price, months, total_predicted_usage, purchase_qty, purchase_cost. months содержит month/year/predicted_usage. Длина months равна горизонту 1–3. Расход суммируется по услугам; purchase_qty=max(0, суммарный расход+минимальный запас−остаток), стоимость округляется исходным Python round до двух знаков. Прогноз количества записей использует Python round; новые правила округления закупок пока не добавлены.

Цена: массив service_id, current_price, suggested_price, difference, difference_pct, is_active. Названия услуг, которые добавлял Rails job, не восстанавливаются без дополнительного поля справочника.

Модель и метрики пока сохраняются в исходных *_model.pth и *_metrics.json; универсальная схема комплекта будет введена в итерации 6. Проверка полной совместимости checkpoint со схемой не относится к текущему валидатору входных таблиц.
