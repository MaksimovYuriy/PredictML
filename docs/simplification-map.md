# Карта упрощения структуры PredictML

Статус: предложение для обсуждения, код не реорганизован. Карта составлена по текущим модулям после девяти итераций адаптации. Планы пособий по разработке и эксплуатации будут согласованы после знакомства с предоставленными теоретическими текстами и презентациями; этот документ их не подменяет.

## 1. Задача упрощения

Сделать путь от таблицы до прогноза понятным при последовательном чтении кода. Сейчас структура частично отражает историю переноса: отдельные оболочки для универсальных таблиц и ServiceFlow, разные точки сравнения, несколько слоёв сохранения. Простое объединение файлов не уберёт эти переходы.

Целевой результат:

- одна точка выполнения обучения/прогноза для интерфейсов;
- общий тренер и единый способ представить обученную модель;
- предметная логика спроса, закупок и цены явно отделена;
- минимальное количество файлов для обычного табличного сценария;
- хранение/история и совместимость не мешают читать алгоритмы;
- тесты и документация описывают назначение, а не номера прошедших итераций.

Не меняем одновременно с этим методику обучения, состав признаков, формулы, критерий выбора весов, разбиения и правила контроля. Изменения поведения, если потребуются, рассматриваются отдельно.

## 2. Предлагаемая структура

```text
predictml/
    __init__.py
    __main__.py
    config.py             # настройки обучения и сценариев
    data.py               # CSV/XLSX, схема и валидация общей таблицы
    preprocessing.py      # сохраняемый конвейер признаков
    models.py             # baseline, linear, MLP и состояние регрессора
    training.py           # общая оптимизация, validation, early stopping
    evaluation.py         # метрики, контроль, сопоставимые прогнозы
    prediction.py         # применение схемы/предобработчика/модели
    workflow.py           # пользовательские операции, связывающие компоненты
    updating.py           # scratch-retrain и продолжение сохранённой MLP
    reporting.py          # таблицы, графики и экспорт отчётов
    demo.py               # доступ к синтетическим примерам
    cli.py

    scenarios/
        demand.py         # календарь, лаги, рекурсия спроса, временная оценка
        materials.py      # нормативы расхода, остатки, закупка, стоимость
        price.py          # подготовка и правило рекомендации цены
        serviceflow.py    # чтение/подготовка экспорта ServiceFlow

    storage/
        repository.py     # SQLite, запуски, версии и их связи
        bundles.py        # комплект, manifest, целостность и загрузка

    ui/
        app.py            # Streamlit-экраны и небольшие UI-помощники
        launcher.py       # запуск локального сервера

    data/examples/        # ресурсы устанавливаемого пакета

examples/                 # канонические примеры для работы с файлами
scripts/                  # сборка/приёмка/синхронизация примеров
tests/
docs/
```

Имена предварительные. В частности, оставляем storage и ui небольшими пакетами: объединение всего хранения и всех экранов в один файл увеличит размер файлов без выигрыша в понимании. Совместимость с legacy рассматривается отдельно ниже, а не смешивается с основными scenarios.

## 3. Карта «сейчас → после упрощения»

| Текущий компонент | Куда переносится | Что именно меняется |
|---|---|---|
| config.py | config.py | Сохраняем настройки; убираем дублирование стандартных значений между CLI, UI и операциями |
| tabular/io.py | data.py | Общее чтение, листы и предпросмотр |
| tabular/schema.py | data.py | Схема, семантические типы, проверки чисел/дат и совместимости |
| tabular/preprocessing.py | preprocessing.py | Сохраняем текущий train-only sklearn-конвейер; не смешиваем его с загрузкой файлов |
| models/mlp.py и models/__init__.py | models.py | MLP размещается рядом с общим представлением регрессора; пустой дополнительный уровень пакета не нужен |
| regressors.py | models.py + training.py | Построение/применение регрессоров — models; обучение и сравнение кандидатов — training/workflow |
| training.py | training.py + scenarios/demand.py + scenarios/price.py | Общая оптимизация остаётся; выбор разделов по названию ServiceFlow-сценария выносится из общего тренера |
| metrics.py | evaluation.py | Один публичный расчёт MAE/MSE/RMSE/wMAPE/R² с едиными правилами неприменимости |
| inference.py | models.py + prediction.py | Применение весов/коэффициентов — модели; схема и полный путь прогноза — prediction |
| tabular/application.py | workflow.py + training.py + prediction.py + storage/bundles.py | Разделяем связку операций, обучение, применение и сериализацию; нынешний TabularModel не должен одновременно управлять всем циклом |
| pipeline.py | workflow.py | Убираем отдельную общую оболочку только для ServiceFlow |
| demand_pipeline.py | workflow.py | Пути, вызовы хранилища и запись результатов не относятся к алгоритму спроса |
| demand.py | scenarios/demand.py | Сохраняем причинные признаки, историю, рекурсию и прикладную временную оценку; общий вывод отчётов остаётся снаружи |
| purchasing.py | scenarios/materials.py | Основное назначение этого модуля — закупки. Нынешний scenarios/materials.py выполняет старый смешанный прогноз и не является его эквивалентом |
| scenarios/price.py | scenarios/price.py | Подготовка признаков, формула и перевод отношения в цену — один предметный модуль |
| comparison.py | workflow.py + evaluation.py + scenarios/* | Оркестрация — workflow, общие показатели — evaluation, специфические правила спроса/цены — соответствующие сценарии |
| version_comparison.py | workflow.py + evaluation.py | Выбор/загрузка версий не относится к математике сравнения; разделяем эти части |
| provenance.py | evaluation.py, отдельная внутренняя секция | Сохраняем отпечатки и проверки независимости, но не вводим для читателя ещё одну публичную точку входа |
| updates.py | updating.py + workflow.py | Изменение модели и фиксированный предобработчик — updating; Store/файлы/регистрация — workflow |
| storage/store.py | storage/repository.py | Оставляем SQLite-операции и транзакции; сценарные вызовы не добавляем |
| storage/bundles.py | storage/bundles.py | Сохраняем проверку комплекта и окружения; читается отдельно от обучения |
| storage/specs.py | storage/bundles.py + сценарные функции метаданных | Убираем отдельный служебный модуль; описание конкретного сценария не прячем в универсальном сериализаторе |
| storage/operations.py | workflow.py + reporting.py | Предсказание по ID — workflow/prediction; CSV/XLSX и представление метрик — reporting |
| reporting.py | reporting.py | Один модуль формирования отчётов; он получает готовые результаты и не выбирает модель |
| ui/helpers.py | ui/app.py | Небольшие вспомогательные функции рядом с экранами; при росте UI позднее делится по страницам, а не произвольно |
| ui/app.py, ui/launcher.py | те же пути | Сохраняем запуск и экраны; все действия вызывают единый workflow |
| cli.py | cli.py | Парсинг и сообщения; одинаковые настройки с UI и общие публичные операции |
| demo.py, data/examples | без функциональных изменений | Установленный wheel должен оставаться самостоятельным |

Таблица описывает распределение ответственности, а не механическое переименование: часть нынешних файлов нужно разделить между несколькими целевыми модулями.

## 4. Что важнее уменьшения количества файлов

### Единый пользовательский путь

```text
таблица → проверка схемы → разбиение → fit предобработчика на train
        → обучение кандидатов → выбор по validation → итоговая оценка
        → сохранение → применение выбранной версии
```

CLI и Streamlit должны вызывать одни и те же операции workflow. Сейчас аналогичные действия проходят через tabular/application, pipeline, demand_pipeline, comparison и storage/operations. Именно эти пересечения упрощаем в первую очередь.

### Направление зависимостей

- data/config/preprocessing/models не знают о Streamlit и SQLite.
- training работает с подготовленными массивами и явно переданной validation-оценкой; не разбирает названия материалов/цены.
- evaluation получает факты/прогнозы и описание наблюдений; не загружает версии из Store.
- prediction применяет уже обученные компоненты, не запускает fit.
- scenarios описывают предметные преобразования и ограничения, а не каталоги запусков.
- storage сохраняет и восстанавливает комплект, но не решает, какую модель обучать.
- workflow связывает эти компоненты и регистрирует результаты.
- reporting получает готовые данные; ui/cli вызывают workflow.

Это устраняет нынешние обратные связи, например обучение, зависящее от подготовки цены, и сравнение версий, импортирующее проверку семейства из updates.

### Без нового слоя абстракций ради абстракций

На данном этапе не нужны фабрики плагинов, контейнер внедрения зависимостей, отдельный класс для каждого шага и обширная иерархия моделей. Достаточно небольших функций и нескольких явных структур данных. Точные сигнатуры согласуем после теоретических материалов и проверки границ рефакторинга.

## 5. Старый режим и эталоны

Сейчас существуют два разных назначения:

- рабочий demand-v2 — исправленная методика;
- legacy-parity и tests/reference — воспроизведение исходного ServiceFlow.

Рекомендация: основной код и объяснение строить на demand-v2. Эталоны оставить в tests/reference. Если старые команды действительно нужны пользователю, их рабочую поддержку изолировать в явно обозначенном compatibility-модуле, сохранив входные контракты. Если поддержка больше не нужна, отдельно согласовать удаление исполняемого режима, оставив эталонные тесты и отчёт переноса.

Пока ничего не удалять: исходное ТЗ и текущие команды включают совместимость. Старую метрику wMAPE с нулём при нулевом знаменателе нельзя незаметно смешивать с корректной общей метрикой.

## 6. Тесты, документация и примеры

| Сейчас | Предлагается |
|---|---|
| test_iteration1…9.py | Тематические test_data, test_preprocessing, test_training, test_evaluation, test_demand, test_materials, test_storage, test_updates, test_ui, test_packaging |
| Проверки разных задач в одном iteration-файле | Перенести по поведению, сохранив все проверки, не просто переименовать файл |
| tests/reference | Сохранить как исторические эталоны, отдельно от базовых примеров чтения кода |
| docs/iteration-*.md | Перенести в docs/history после обновления ссылок; это журнал, не пользовательское руководство |
| Контракты, архитектура и руководства | Оставить актуальными документами верхнего уровня; обновить после фактического рефакторинга |
| examples и пакетная копия data/examples | На первом этапе оставить синхронизацию и проверку совпадения: это обеспечивает работу wheel вне репозитория |
| Приёмочные scripts | Оставить как проверку поставки; не смешивать с обычным обучением моделей |

Перестройка тестов не должна создавать впечатление увеличения покрытия за счёт смены названий. На последней приёмке было 63 теста; перед рефакторингом нужен новый фактический базовый прогон и перечень проверяемых поведений.

## 7. Порядок безопасного перехода

| Шаг | Изменения | Критерий завершения |
|---|---|---|
| 0. Зафиксировать базу | Текущие тесты, CLI/UI-сценарии, контрольные веса/прогнозы и загрузку имеющихся комплектов | Известно, что именно должно сохраниться |
| 1. Общие простые компоненты | data, preprocessing, models, единые метрики и настройки | Те же схемы/предобработка/численные результаты; старые входы доступны через временные переэкспорты |
| 2. Предметные сценарии | Спрос/закупки/цена/экспорт ServiceFlow в scenarios | Одна функция признаков для обучения/прогноза, прежние контрольные примеры проходят |
| 3. Единый workflow | Объединить оболочки train/predict/compare/update и подключить CLI/UI | Один исполняемый путь на действие; старые команды и экраны работают |
| 4. Хранилище и обновления | Упорядочить bundles/repository, вынести IO из вычислений | Предыдущие версии читаются либо есть отдельно согласованная явная миграция |
| 5. Учебная навигация | Тематические тесты, актуальные документы, история отдельно | Путь таблица→модель→прогноз можно проследить без чтения всей истории проекта |
| 6. Повторная приёмка | Установка wheel, полный CLI/UI, обновления и контроль | Все согласованные сценарии воспроизводятся вне исходного checkout |

Особый риск: pickle/joblib хранит пути Python-классов. Простое перемещение TabularModel, Preprocessor или MLP может нарушить загрузку старых файлов. Переэкспорты/модули совместимости нужно держать до проверки реальных сохранённых комплектов; удалять их только по отдельному решению. Версия формата и политика миграции не меняются молча.

## 8. Как карта поможет последующим пособиям

Это опорные блоки содержания, а не утверждённый план глав:

| Читателю нужно понять | Где это будет видно в коде |
|---|---|
| Из чего состоит обучающая таблица и что прогнозируем | data/config и пример конфигурации |
| Почему статистики учат только на train | preprocessing и разбиение в training |
| Чем отличаются baseline, linear и MLP | models и общий цикл training |
| Как честно сравнить результаты | evaluation и отчёт |
| Как получить прогноз после перезапуска | prediction и сохранённый комплект |
| Как применить модель к задаче спроса/закупок | scenarios/demand и materials |
| Почему рекомендация цены не равна прогнозу рынка | scenarios/price и происхождение цели |
| Как продолжать обучение без изменения входного пространства | updating и фиксированный preprocessor |
| Как пользоваться готовой программой | UI/CLI и пользовательское руководство |

Разработку и эксплуатацию не следует автоматически считать одним пособием. После получения теории и презентаций сопоставим термины/последовательность, определим предварительные знания, распределим материал между пособиями и только затем утвердим их планы.

## 9. Решение на текущем этапе

Рекомендуется переход к более плоскому ядру с отдельными scenarios, storage и ui. Сначала сокращаем дублирование пользовательских путей и обратные зависимости, затем объединяем файлы. Рефакторинг, удаление legacy и изменение формата моделей этим документом не выполнены и не утверждаются автоматически.

После получения теоретического DOCX и трёх презентаций подготовлено сопоставление: [course-alignment.md](course-alignment.md). Там отмечены расхождения старой относительной цели спроса с demand-v2 и предложены границы пособий по разработке и эксплуатации. Эти предложения ещё не являются утверждёнными планами.
